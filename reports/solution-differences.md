## 0. 總結：十點

1. **AMF 在控制路徑之爭裡有四種角色，不是二選一**：全權中介、純轉送容器、只做開機引導、完全不在。P4a 排除了前三種。依字面，連 #1 用 N1N2Transfer 做的開機引導（¶492）也在排除之列（分析）。
2. **P4a 留下一個沒有寫明的缺口：gNB 第一次怎麼找到 SF？** 39 個方案裡，明文描述「不經 AMF 的初始互相發現」的只有三種：
   - OAM 預先設定位址：#21 ¶1706、#16 ¶1475、#35 ¶2585、#36 ¶2659
   - gNB 主動建立傳輸層關聯：#16 ¶1474
   - gNB 自己查 NRF：#15 ¶1408
   §8.3 NOTE 1 與 §8.4 NOTE 3 就是這個缺口。
3. **資料傳輸有六種模型，結論只定了兩件事。** 一是控制端點和資料端點可以不同（§8.4 第2點）；二是「交換連線資訊後直連」（§8.4 第3點，字面取自 #18 ¶1573）。實際承載方式全部交給 RAN3。
4. **SCF/SPF 切分被降格，但留了多實例的空間。** P1 只把切分保留為 SF 內部選項，而且 "no standardized interface"，等於把 #19、#24、#12 的「兩個 NF＋標準介面」降格。但 NOTE 3 寫的是 "SPF(s)"，複數形保留了多個處理實例的部署空間。
5. **授權有六種模型，結論選了 AF 中心的靜態表。** 表格的血統可以追溯：#9 的 Table 6.9.1-1 → #37 ¶2756 補上 forbidden 與 service type → Table 8.2-1。
6. **§8.2 d 的撤銷條件字面取自 #11 ¶1109**："authorization criteria are no longer met"。
7. **§8.5 第4點的請求參數**："sensing time parameters" 與 "requested Sensing QoS" 字面取自 #27 ¶1975、¶1980；"AF Identifier" 取自 #28 ¶2081，#9 ¶941 也有。
8. **§8.6 的參數清單**：目標區、sensing service duration、回報型態分別對應 #35 ¶2597 的 "sensing duration" 與 #39 ¶2837 的 "Periodic, one-time"。「SF 推導參數」對應 #34 ¶2527–2529 的兩段式參數。
9. **四個橫切面問題 §8 完全沒處理**，但多個 solution 各給了不同答案：識別碼體系、區域表示法、gNB 能否拒絕或回報可行性、處理與事件判斷放在 gNB 還是 SF。這些是規範階段最可能爆發分歧、也最可能出現新專利申請的地方（推論）。
10. **UE 的各種參與方式在 Rel-20 全部擱置。** 消費者、目標、感知實體、同意、發現等角色，在 39 個 solution 裡各有機制，而且都建立在 AMF/NAS、LCS、PDU Session 等既有機制上。

## A. 控制信令路徑：AMF 扮演什麼角色

**技術問題**：SF 要對 gNB 下指令（建立、修改、終止感知任務），指令走哪條路。

| 變體 | AMF 的角色 | 代表 | 原文要件 | 技術取捨（分析） |
|---|---|---|---|---|
| A1 全權中介 | 選 gNB、轉送請求、轉送資料 | #5 | AMF 負責 "Discovery and selection of sensing entities" 與 "Forwarding the sensing request" ¶685–686；資料經 AMF，AMF 可合併多台 gNB 的通知 ¶731；自承 "applicable as long as the N1/N2 interface will not be overloaded" ¶738 | 可以重用 AMF 對 gNB 的掌握，但 AMF 變成感知資料的匯流點，負載與時延直接受 N2 限制 |
| A1′ 中介＋能力倉庫 | 存放 gNB 感知能力，供查詢或事件通知 | #13、#17、#39 | SEMF 向 AMF 訂閱目標區內的 SE ¶1269；Namf_EventExposure ¶1550；AMF "collates information on the capabilities" ¶2827 | 能力資訊集中在 AMF；但 gNB 怎麼把能力報給 AMF 本身沒有現成程序（#169 主席在 #17 加了 EN） |
| A2 純轉送（容器） | 只轉不讀 | #35 b 案、#7、#18 | "Sensing Service Container"，AMF 只看容器外的 NG-RAN ID 與 SSF ID ¶2598；Namf_SS_ParameterDelivery ¶2606；#7 用 Namf_SensingCfg_Request ¶853、NGAP SensingDataReport ¶855；#18 用 N1/N2 container 送連線資訊 ¶1581 | 看似改動最小，但 TS 38.413 沒有通用的非 UE 關聯傳輸程序（Qualcomm S2-2600580），仍要新增 NGAP 程序。#39 也承認要比照 "RAN configuration update" 新增 "Sensing Configuration Update" ¶2840 |
| A3 只做開機引導 | 轉送一次設定觸發，之後退出 | #1 | SF "invoking the Namf_Communication_N1N2Transfer service" 送觸發，gNB 依提供的位址建立 TLS，此後 "without going through other core network control functions, e.g. AMF" ¶492 | 解決「找得到 gNB」，之後又不負擔 AMF；但 P4a 的 "without AMF involvement"（¶2930）字面上也排除了這一步（分析） |
| A4 完全直連 | 不在路徑上 | #21、#26、#16 a 案、#34、#35 a 案 | OAM 事先把 NG-RAN 的 IP 設定給 SF ¶1706；SCF 與 gNB 之間 "a new interface" ¶1879、¶1915；OAM 預設 SF ID 清單 ¶1475 | 規格乾淨，與通訊業務隔離；代價是 SF 要自己維護 gNB 清單、連線與安全 |

- **結論落點**：P4a（¶2930）、P4b（¶2931）。#173 舉手表決 Option A：支持 19、不支持 6、反對 3（S2-2601706）。
- **被吸收的技術特徵**：
  - #1 列出的直連介面五項要件（¶462–466：大量資料不影響 UE 服務、QoS 時延、可被多個 SF 重用、SF 控制與設定、安全保護），成為直連方的論證基礎。
  - #26 的 SCF–gNB 新介面就是 P4a 的形態。
- **規範階段的缺口**：
  - **初始發現**：P4a 之下，gNB 怎麼得知 SF？只剩 OAM（#21、#16 a 案、#35、#36）、gNB 主動建立關聯（#16）、gNB 查 NRF（#15）三條路。最後一條要 gNB 當服務化介面（SBI）的消費者，在現行架構中罕見。
  - **連線規模**：SF 數量 × gNB 數量的連線維護成本，是 Nokia 等在 S2-2600619 提出的論點，沒有被正面回應。
  - **多 SF 分工**：#16 的 "redirection indication and corresponding target SF ID"（¶1482）可以處理多 SF 分工，但在 P5（一請求一 SF）之下用途有限。

## B. 感知資料傳輸

**技術問題**：gNB 量到的資料可能很大，要怎麼送到核心網，又怎麼對應到是哪一個請求。

| 模型 | 代表 | 機制要件 | 綁定方式 | 取捨（分析） |
|---|---|---|---|---|
| B1 經 AMF | #5、#7 | 資料經 N1/N2 ¶690；NGAP SensingDataReport → Namf_SensingDataTransfer ¶855–856 | 隨 NGAP 訊息 | 控制面承載大量資料，#5 自承以「不過載」為前提 |
| B2 同一介面裝容器 | #21 | DL/UL Service Message Transfer 承載 sensing request、response、report ¶1712–1717 | SF 配發 correlation ID ¶1712 | 控制與資料共用一個通道，簡單；資料量大時會和控制訊息互相排擠 |
| B3 獨立資料連線＋綁定 | #18 | 經控制信令交付 connection information（IP）與 binding information ¶1573；連線建好後，gNB 回送 binding info ¶1585 | SE ID、connection ID 或 binding ID ¶1573 | 控制和資料分開；多一個綁定步驟 |
| B4 隧道 | #22、#26 | 雙方交換 TEID 及/或 IP ¶1727、¶1735–1737 | 資料夾帶 Sensing service ID ¶1741；#26 把 Sensing Task ID 放在傳輸標頭，區分同一台 gNB 為不同任務產生的多份資料 ¶1918 | 類似既有的使用者面隧道，適合大量資料；隧道協定待定（EN ¶1739） |
| B5 sensing session 直達處理端 | #25 | SCF 依 sensing area、SPF capabilities、load、location 等選 SPF ¶1857，取得 SPF 的連線設定後轉給 gNB ¶1858–1859 | Sensing Session ID ¶1859 | 控制端點（SCF）與資料端點（SPF）明確分開；連線可以重用 ¶1846 |
| B6 獨立資料收集功能 | #24（SDCF）、#7（DCCF） | SSMF 附上 SDCF 端點 ¶1817；SDCF 依 "sensing data specification" 收集與處理 ¶1818 | 訂閱關係 | 多一個 NF；可以快取（資料已存在就跳過量測 ¶1818） |

- **結論落點**：
  - §8.4 第2點 "different Endpoints for control signalling messages and for sensing data Report"（¶2970）及 NOTE 2 → B5 的 #25，以及 #3 ¶618、#34 的 Nsx-1/Nsx-2（¶2515）
  - §8.4 第3點 "established by exchange of connection information"（¶2972）→ 字面取自 #18 ¶1573
  - §8.4 第5點多台 gNB（¶2976）→ #26 ¶1882
  - B1、B6 出局（P4b、P1）
- **規範階段的缺口**：
  - B2、B3、B4、B5 選哪一種，交給 RAN3（§8.4 NOTE 3，¶2973）
  - 綁定用的識別碼（見 X1）
  - 一次性或週期性回報（§8.4 NOTE 4，¶2975）

| C6 重用分析或資料框架 | #7（DCCF＋ADRF ¶836）、#24 | — | #169 主席刪除一處 NWDAF/ADRF 描述（¶836 仍保留 ADRF 選項）；P1、P2 排除 |

**技術核心（分析）**：
- 標準化的 NF 間介面，好處是多廠商可以互通，代價是規格量大。
- P5「一個請求只選一個 SF」直接切斷了多 SF 協作（C3、C4 的分散端、C5）。結果是：一架無人機飛越多個 SF 的服務區時，Rel-20 只能靠 SF 內部處理，或靠 gNB 重選（§8.3 第7點），不能把任務交接給另一個 SF。

## 3. 規範階段的技術預判（推論，只依附上列 solution）

1. **直連的建立**：最可能的樣板是 #16 的 gNB 主動建立關聯（類似 NG Setup），搭配 OAM 預設的 SF 清單（#16 a 案、#21 step 0）。它是 39 個方案裡唯一完整描述「不經 AMF、由 gNB 端建立、含失敗重導」的程序（¶1474–1482）。
2. **資料承載**：#22 的 TEID 隧道加上 #26 的標頭 Task ID，最能同時滿足「大量資料」與「多個任務共用一台 gNB」。#21 的同介面容器較適合少量的控制與事件回報。兩者可能並存，分別承載兩類訊息。
3. **部分授權**：#37 ¶2757「只對已授權的部分區域繼續執行」是現成的條文。
4. **gNB 回饋**：#22 的接受指示、#16 的 confidence level、#36 的事件通知，至少會有一種進入 RAN3 的訊息設計。
5. **識別碼**：會出現三層：
   - 請求層，類似 #9 的 AF Transaction ID 或 #14 的 coordination ID
   - 任務層，類似 #11 的 Sensing Service ID 或 #26 的 Task ID
   - 連線層，類似 #25 的 Session ID 或 #18 的 binding ID

**SEP 讀入要點（推論）**：
- 最可能出現在 Rel-20 TS、成為比對要件的：
  - 控制端點與資料端點分離
  - 交換連線資訊後直連
  - 依 supported sensing area 選 SF 與 gNB
  - AF 授權資料表（含 Not allowed area）
  - SF 依結果更新參數
- Rel-20 讀入可能性低的：請求項以下列任一項為必要要件者——AMF 轉送、AMF 存放 gNB 能力、多 SF 協作、專用儲存 NF。
